# TCF 0.8.4, news source

Dated document that feeds the channel texts in [`linkedin/`](linkedin/). Rule: no channel text
changes without this source changing first.

Nothing here is an estimate, and **the numbers have no verifier of their own**. They live where
they already lived: the canonical sizes in `tests/test_regression_v1_baseline.py`, which pins
them byte for byte and runs the round-trip of the §RT rule; the real-data gains in the dated
EXP-019 report; the timings in the pinned baseline of `scripts/bench_perf`. A second instrument
measuring the same thing would only create a second truth to diverge from the first.

What this page adds is that **the blocks below run**. They are in `test_docs_snippets.py`,
alongside the README and the reference, so an example that rots fails the suite.

## What the library is

It compresses tabular text losslessly, and the result stays text you open and read. A dict of
columns goes in, a string comes out, and it comes back identical. It is not a database, not
ETL, and not a binary format.

`pip install tcf-format` · MIT · pre-1.0 · Python 3.10 or newer · zero dependencies.

The public surface is 18 names. The suite has 2005 tests passing and 2 skipped.

## The headlines, in the order that matters to someone new

### 1. The question almost everyone asks is misplaced

The question is "TCF or gzip?", and it does not hold up, because the two do not compete for the
same spot.

In transmission, `Content-Encoding` is negotiated by the transport and is **invisible to your
code**. You do not choose it against anything, and most of the time you never see it: by the
time your handler reads the body, it has already been inflated. So the honest question is not
"TCF or brotli", it is **what my process holds and parses once the channel has done its
invisible work**.

That does not make the channel free. It spends memory and CPU to inflate, on every request, and
the bill is just paid one layer down, where your code does not see it. It is part of the total,
not outside it.

### 2. Where the compressor becomes a visible decision, it charges opacity

On disk, in blocks, the compressed blob is the thing you own. And there the price transmission
was hiding shows up: **to read anything, you inflate everything**. There is no reading one
column, counting one value, or filtering one row before the whole payload exists again.

TCF sits in between: compressed and still queryable.

```python
from tcf import decode, encode, view

table = {
    "nome":   ["Ana Souza", "Bruno Lima", "Carla Nunes", "Diego Rocha"],
    "email":  ["ana@acme.com.br", "bruno@acme.com.br",
               "carla@acme.com.br", "diego@acme.com.br"],
    "cidade": ["Sao Paulo", "Sao Paulo", "Sao Paulo", "Rio de Janeiro"],
    "plano":  ["Premium", "Premium", "Basic", "Premium"],
    "cpf":    ["111.111.111-11", "222.222.222-22",
               "333.333.333-33", "444.444.444-44"],
}

wire = encode(table)
assert decode(wire) == table               # §RT: the round-trip comes before the number
assert len(wire.encode("utf-8")) == 242

v = view(wire)                             # nothing decoded yet
assert list(v.columns) == ["nome", "email", "cidade", "plano", "cpf"]
assert v.nrows == 4
assert sorted(v.distinct("cidade")) == ["Rio de Janeiro", "Sao Paulo"]
assert dict(v.group_count("plano")) == {"Premium": 3, "Basic": 1}
assert v.where("plano", "Premium").nrows == 3
assert v.column_bytes("cpf") == 59         # you can ask what each column costs
```

None of those calls decodes the whole table. And the assertions are not decoration: this block
runs in the suite, so the `242` above cannot go stale silently.

### 3. The numbers, on the same footing

Four records, five columns, every format measured **compact**, which is the fair comparison:

| format | raw | gzip | br | zstd |
|---|---:|---:|---:|---:|
| JSON | 451 | 206 | 195 | 197 |
| JSONL | 449 | 205 | 194 | 194 |
| CSV | 277 | 177 | **162** | **165** |
| **TCF** | **242** | 206 | 185 | 193 |

TCF is the smallest **raw** among the formats an API actually sends. Under `gzip` the three tie
within 1 B. And CSV, which is rarely an API payload, is smaller once compressed at this tiny
size.

On larger sets the distance opens up. Across the 8 real datasets of
[EXP-019](../../experiments/lab/clean/EXP-019-consistencia-0-8-4/), the set fell from 390,863 B
to 290,949 B, or **−25.6%**, ranging from −4.1% to −46.6% depending on the data. On real
multi-column data, 9 Adult and TPC-H tables with 136k rows, it is **−33.02% weighted** against
raw CSV.

### 4. The same data nested, which is the JSON your API sends

Since 0.8, TCF reads the **dataset** your language builds from JSON, not the JSON text. Nested
objects, arrays, `null`, and typed `true`/`false` round-trip byte for byte.

Two records with a list inside: compact JSON is 184 B, TCF is 166 B, and with the opt-in CPF
filter it is **144 B**.

What it does is shred the object into columns, one per field. So the field name is written
**once** in the header, not once per record:

```
#TCF.8Hnome:21,cpf:38,ativo:11b,fones#:6[
```

### 5. The contract: never worse than the alternative, and knowable up front

The library makes a verifiable claim about size, not a promise.

> For each column, the encoder generates the candidates and writes the **smallest**:
> `min(tcf, raw, dictionary, split)`. The result is **never worse by construction**.

That changes what the decision costs. You do not need to test whether the format made your data
worse, because the encoder's structure does not allow it to. The worst case is tying with the
raw representation, and the cost of the tie is the header.

`sort_by` is the example of the rule applying when something new comes in. It does not sort, it
**proposes** a sort, and the FLOOR decides whether it lands. The reason not to sort outright is
measured: on a 60-row table, sorting by a key shrinks it 43.0% when the other columns are a
function of that key, and **grows it 52.1%** when they are independent, because the permutation
groups the key's equals and scrambles everything else. Across the seven measured cases, letting
the FLOOR decide avoids 734 B of loss.

### 6. How the contract is verified

Three things, and none of them is the suite passing.

**The §RT rule**, which is process and not code. It is written as an invariant in the project
guide, and says `decode(encode(x)) == x` comes before any number: without a round-trip, the
number does not enter prose, a table, or a commit.

**The byte-canonical gates**, which pin the expected output of known sets and fail red if a byte
changes. That is what stops an optimization from changing the wire unnoticed.

**The pinned performance baseline**, with the case matrix locked by hash. It refuses to compare
two runs when the matrix or the plan differ, rather than joining what does not join.

### 7. Writing is expensive, reading is cheap, and that is deliberate

The work is concentrated in `encode`. `decode` is a single linear pass, with O(1) lookups and no
search, and `view` is less than that, because it reaches values by arithmetic instead of
walking.

The ratio **is not constant**: measured on 0.8.4, it ranges from 3.6x to 1,060x depending on the
shape of the data, so it is a range and not a number.

That decides where the format pays off, and topology matters more than client versus server. If
the data is **cacheable**, you pay the encode once and distribute many times. If it is
**personalized per request**, you pay the encode every time, and the arithmetic changes.

### 8. Repetition has three shapes, and two of them are not obvious

`*N|` collapses identical adjacent rows, which is what most people expect from RLE. The other
two are the ones that show up in system data.

`*N+delta|` covers a sequence with a constant step: `[100, 105, ... 155]` comes out as
`*12+5|\100`, 47 B becoming 18, with none of the twelve values written down. And
`*N~d1,d2,...|` covers a periodic sequence, when the step cycles: the cycle is paid once and
covers the whole run.

That matters beyond the byte, because a `*N|` **is already a count** and a `*N+delta|` **is
already a progression**. It is what lets `view` answer about counts, minimum and maximum without
materializing the column.

## Where this applies today

**The `.8` closed functionality, not performance.** The four wire families are welded and
published. The algorithm optimization cycle is the `.9`, and it has not started, so the timings
above come from unoptimized code. They are pinned precisely so the `.9` has something to compare
against.

**Under `gzip`, TCF does not win.** The three formats tie within 1 B on the small record set.
Where it wins is raw, under `br` and under `zstd`.

**At tiny sizes, CSV beats it.** 162 B against 185 B under brotli. Worth noting that CSV is
rarely an API payload, and that it has no `view`.

**It is pre-1.0.** The middle digit can still change what comes out, and every change enters the
changelog with the measurement behind it.

**Comparison against storage formats has not been done.** Parquet, ORC and the like occupy a
different place and deserve their own measurement, which does not exist.
